F-1  pi-worker-context asserted an external-API fact it has no tool to check, and
     attributed it to live docs.  [SEVERITY: caused total product failure]

  WHAT IT WROTE (TASK_0027.md, CONTEXT block, verbatim):
    "The `hono` dependency is pinned at `^4.12.31` in package.json, and the external
     context confirms `hc<AppType>` pattern with base URL `/api` for same-origin relative
     paths works correctly (per Hono RPC docs LIVE data)."

  VALIDATED FACTS:
    a) worker:context is given tools `read,grep` ONLY — src/task/phases.ts:623.
       It cannot call pi-worker-docs, pi-worker-fetch or pi-worker-search. The claim
       about hono's RPC client behaviour was therefore NECESSARILY from model memory.
    b) No "Hono RPC docs LIVE data" exists anywhere in research-cache.json. The
       attribution is fabricated. (grep over all 248 entry values.)
    c) The one real hc lookup returned only a type signature with zero usage semantics:
         key: pi-worker-docs hono/client::hc factory function signature base url parameter
         body: "hc ... takes two parameters: baseUrl of type Prefix and an optional
                options of type ClientRequestOptions."
       and the direct usage question returned "unclear from this package":
         key: pi-worker-docs hono::how to use hc<apptype> from hono/client for typed rpc
              client. how does the chaining work? ...
    d) RESEARCH_CONTEXT_PROMPT's LIVE-DATA RULE (src/task/prompts.ts:191–195) constrains
       ONLY version numbers and service status ("### npm:", "### service:",
       "### freshness-check skipped"). There is NO rule governing API *usage* claims, and
       nothing verifies that a "per LIVE data" attribution corresponds to a real block.
    e) MECHANISM: one citable fact (the pinned version, genuinely from EXTERNAL CONTEXT)
       was fused in a single sentence with an uncitable claim (base URL semantics) under
       one shared attribution. The true half laundered the false half.

  DOWNSTREAM: TASK_0027's spec promoted it to a hard requirement in BOTH sections —
    CONSTRAINTS: "The base URL must default to a relative path (`/api`)"
    ACCEPTANCE:  "exports a default `api` object ... with base URL `/api`"
  The same spec separately states RPC paths already contain `.api` (the photos note), so
  the spec is internally self-contradictory. Implementation obeyed it exactly:
    src/client/api.ts:4   hc<AppType>('/api')  +  api.api.auth.login.$post()
    ⇒ every request goes to /api/api/... ⇒ 404 ⇒ 100% of the product's API surface dead.
  REPRODUCED: browser load of HEAD emits 5× `404 /api/api/auth/me`; server is fine
  (`curl -X POST /api/auth/login` returns 200 with a valid session).

  MECHANISM (the actual defect): escalation fires when the worker perceives the fact as
  MISSING. A type signature is not missing — it is a well-formed, confident, on-topic
  answer that names the very parameter asked about (`baseUrl`). So it terminates the
  search without supplying the semantics (is it an origin, or a mount prefix?). The
  worker stopped, and worker:context then filled the semantic gap from memory (F-1).
  "unclear from this package" is the HONEST failure and does escalate; the DANGEROUS
  failure is the type signature that looks like an answer.

  SUPPORTING FACTS (validated):
    a) 67 of 248 cached results (27.0%) are an explicit "unclear" non-answer.
    b) The design doc names the answers explicitly. DESIGN/PROJECT.md §5 line 184:
       "...per https://hono.dev/docs/guides/rpc", and §13 lists four hono.dev URLs
       including the RPC guide and grouping-routes-rpc. pi-worker-fetch produced 30
       results: 13 playwright.dev, 11 tailwindcss.com, 4 bun.com, 1 bun.sh, 1 github.com
       — ZERO hono.dev.
    c) Identical shape for the second fatal defect: §13 cites
       https://bun.com/docs/runtime/sql; fetch retrieved bun.com/reference/bun/build,
       /BuildConfig and bun.sh/docs/test/configuration.md — never runtime/sql. The docs
       worker had answered "unclear from this package" to
         "what is the bun sql api? how does `import { sql } from "bun"` work? ..."
       Consequence: src/server/db/migrate.ts:62 executes DDL as `await tx`${content}``,
       sending the whole .sql file as bind parameter $1.
       REPRODUCED on a clean database: `syntax error at or near "$1"` — a fresh install
       of this project cannot create its schema at all.
    d) The pointer was IN the retrieved text and was not followed: the .d.ts excerpts
       pi-worker-docs returns carry `@see {@link https://hono.dev/docs/...}` JSDoc links.
       hono.dev appears in cache values ONLY inside those excerpts, never as a fetch.
    e) Non-answers are cached and re-served as cache hits (details.hitCache === true on
       "unclear" entries), so one dead end is paid for many times. CAUSE, exactly:
       src/workers/pi-worker-docs.ts:362 `cacheable: d => d.childExitCode === 0`. A child
       that ran fine and answered "unclear from this package" exits 0, so the non-answer
       is cached. Cacheability is keyed on process health, not on answer content.

  STRUCTURAL CAUSE: pi-worker-docs reads bundled .d.ts declarations. For a type-only
  declaration (`hc: (baseUrl: Prefix, options?) => ...`) the semantic answer is not in
  the package at all — it lives at the `@see` URL. The worker cannot distinguish "I
  retrieved the type" from "I answered the question".


F-3  pi-worker-fetch: 10 of 30 failures, four distinct mechanisms.
     [SEVERITY: no shipped defect traced to it this run — see (e)]

  (a) FALSE "unclear" — the answer was in the excerpt it had just retrieved. 4 cases.
      Strongest: url playwright.dev/docs/test-components, query "show the exact api of
      the router fixture ... what methods does it have?". Retrieved excerpt reads
      "Call `router.route(url, handler)` ... Call `router.use(handlers)` ..." and the
      answer returned was "unclear from this page". Same shape for Bun BuildOutput
      (excerpt contains "returns a BuildOutput with {success: false}"), Tailwind @source,
      Tailwind `static` theme option. Retrieval worked; the abstention threshold is
      miscalibrated. These are recoverable losses.

  (b) EXCERPT FIELD CONTAINS THE CHILD'S OWN PROSE, not a quote. 4 cases
      (excerptVerified === false). Example, url bun.com/reference/bun/build:
        excerpt: "The page does not list fields for outdir, outfile, splitting, external,
                  or target as direct BuildConfig properties."
      That is a conclusion presented as a quotation, and it is factually WRONG — `outdir`
      is a real BuildConfig field. Another (playwright test-components) stitched a fake
      quote from non-contiguous fragments joined by "....".

  (c) PAGE CANNOT CONTAIN THE ANSWER. 2 cases. Queries "which playwright version
      introduced the router fixture?" and "show the example from v1.46.0" were aimed at
      /docs/release-notes, which covers only 1.61→1.7. The worker reported this itself.
      URL is chosen before page coverage is known; there is no retry against another page.

  (d) URL FRAGMENT DISCARDED. 1 case. Given
      playwright.dev/docs/api/class-locator#locator-set-input-files it returned the page's
      opening paragraph ("Locators are the central piece of Playwright's auto-waiting...")
      and answered "unclear". VALIDATED AT CODE LEVEL: there is no hash/fragment handling
      anywhere in the fetch path — `new URL()` appears in src/workers/html-clean.ts only at
      lines 34, 45, 242 and is used for `.hostname` only. A deep link degrades to a
      top-of-page grab.

  (e) CONTAINMENT WAS LUCK, NOT A GATE. The wrong `outdir` claim in (b) did not cause a
      defect only because build.ts uses `outdir`, `splitting` and `naming` anyway. No gate
      caught the bad research.

  (f) NOT PROVEN — do not act on this without evidence: one of the four
      excerptVerified===false cases (bun.com/reference/bun/BuildConfig) has an excerpt that
      LOOKS like genuine page markup with escaped markdown (`string\[\]`, `[field](/ref/…)`).
      isExcerptInContent (src/shared/child-output.ts:26) is a whitespace-normalised
      substring match with no markdown-escape normalisation, and it is called against the
      full `cleaned.markdown` (src/workers/fetch-core.ts:95) while the child sees a clamped
      copy (25k head + 5k tail, fetch-core.ts:13–15,110). Whether this is a verifier false
      positive CANNOT be determined: the source content is not retained anywhere. This is
      precisely why PROMPT 3 item 4 exists — make the failure diagnosable first, then judge.


F-4  LATENT: pi-worker-docs cannot spawn anything under a Bun runtime.
     [SEVERITY: dormant in production — found while building the STEP 0 harness]

  pi-worker-docs.ts:128–132 selects the spawn primitive:
      internals.spawn ?? (globalThis.Bun !== undefined ? globalThis.Bun.spawn : node spawn)
  but runChild (child-process.ts:385) calls it node-style:
      spawn(invocation.command, invocation.args, {cwd, shell: false, stdio: [...]})
  whereas Bun.spawn's signature is (cmdArray, opts). Under Bun every spawn in that tool —
  the npm auto-install AND the child summariser — throws
      TypeError: cmd must be an array
  REPRODUCED: calling the registered tool from a `bun run` harness fails 3/3 with that
  error, stack through runAutoInstall → docsRaw → run → execute.

  WHY IT IS DORMANT, not shipped-broken: pi runs the extension under node, so the Bun
  branch is never taken in production. Run 15 proves it positively — 95 cache entries
  carry `autoInstalled: true`, i.e. the npm spawn succeeded. Note also that docs-core.ts
  has NO such branch (it uses node's spawn unconditionally), which is why a direct
  docsFocused call works under Bun while the tool does not.

  NOT FIXED HERE — STEP 0 is measurement-only. The baseline harness injects node's spawn
  through the tool's own documented `internals.spawn` hook, substituting the process-spawn
  primitive and nothing else. Decide separately whether the Bun branch should be repaired
  or deleted; it is currently untested and unreachable.

THE MECHANISM, NAMED. A semantics clause is PROSE. Its checkable factual content is the behavioural
ASSERTION ("baseUrl is concatenated", "$url throws on relative"), which carries no ungroundable
symbol. Its code tokens are (a) real API names that ground, (b) standard-platform names correct but
absent from package docs, (c) example placeholders/literals. (b) and (c) are indistinguishable, to
any symbol-grounding rule, from a fabricated symbol — and (a) is where the real fabrications hide.
Symbol grounding measures the wrong thing. PROMPT 1's braces worked because it demoted a whole
unsourced BULLET keyed on a citation it could check; there is no analogous checkable handle on a
one-line prose semantics claim.
