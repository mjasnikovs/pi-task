TASK 3 — THE REQUIREMENT-EXTRACTION LOTTERY (the big one, unfixed)
------------------------------------------------------------------------------
STATUS: STEP 0 COMPLETE, no fix designed. This is the highest-leverage open item
in the planner and it is bigger than everything shipped in v0.23.1.

MEASURED (all on the same byte-identical 20402-char mx5 spec):
  - single-pass extraction yield: 23..146, sd ~36. A 5-6x swing.
  - 208 distinct "requirements" produced across 10 runs; only 5 appear in ALL 10.
  - pre-cap mean pairwise Jaccard 0.485; post-cap 0.423. So the cap makes it
    slightly worse but the lottery is in EXTRACTION, not in capRequirements.
    (I initially suspected the cap and was wrong — do not redo that.)
  - ownable count swings 21..30 => granularityFloor swings 11..15 for identical
    input.
  - THE JUNK IS MORE STABLE THAN THE SIGNAL: 37 schema/DDL rows recur in 6/10
    runs, while the test-cadence obligation appears in 4/10 and "photo upload
    limit" in 1/10.
  - Only 7.9 of 16 critical obligations reach the shipped 40 in a typical run.
    Half the requirements that have historically broken builds are ABSENT.
  - HIGH-YIELD RUNS ARE WORSE: yield 132/143/130 -> 6/5/7 critical obligations;
    yield 24/35/43 -> 11/11/9. Padding crowds out signal before the cap.

RULED OUT — DO NOT RE-PROPOSE
  k-of-n VOTING across passes. Any threshold >=5 keeps all 37 schema rows and
  DELETES the test-cadence line and the "non-/api GETs serve the built
  index.html" clause — the two whose loss has already cost a run each (run 11
  and run 16 respectively). Voting stabilises junk and deletes signal here.

THE ACTUAL FIX SHAPE
  The 40-slot budget must be allocated by OBLIGATION-BEARING-NESS, not by
  recurrence and not by section round-robin alone. capRequirements currently
  does marked-passage priority then sectionFairFill. Section fairness exists for
  a real reason (run 16: a plain first-N cap cut all 138 entries past the cap,
  every one from the design's tail, including the clause whose loss shipped a
  blank app) — so any new ranking MUST preserve tail coverage. That tension is
  the design problem.

  Union-across-passes raises recall but makes selection binding harder (union of
  10 passes = 208 quotes for 40 slots), so it only helps if selection improves
  first. Sequence: selection, then consider union.

MEASUREMENT ALREADY BUILT (reuse, do not rewrite)
  scripts/extraction-stability-step0.ts   count + set churn, pre/post cap
  scripts/extraction-precision-step0.ts   per-run pools -> extraction-pool.json
  scripts/extraction-filter-score.ts      offline filter scoring + FP suite
  scripts/extraction-filter-endtoend.ts   filter -> cap -> critical-obligation count
  The end-to-end script is the right metric for ANY selection change: it replays
  recorded runs offline (instant) and counts critical obligations reaching the
  shipped 40. Design against that, then confirm live.

PASS CONDITION FOR ANY SELECTION FIX
  Critical obligations reaching the shipped 40 must rise materially above the
  7.90 baseline with ZERO losses, AND tail-section coverage must not regress
  (check that quotes from the doc's last sections still appear — that is what
  sectionFairFill protects).

TIME: design cycle, not a patch. Offline iteration is instant; live confirmation
~30 min per candidate.

TASK 4 — THE COVERAGE LOOP'S SPLIT-BRAIN GATE (design, blocked on TASK 3)
------------------------------------------------------------------------------
STATUS: OPEN, deliberately deferred. This is the ROOT CAUSE of the warning that
started all of this ("/task-auto: no task fully owns — ...").

THE DEFECT
  The loop's CONTINUE condition and its ADOPT condition read DIFFERENT signals:
    continue: best.plan.missing.length === 0
              missing = holistic judge free-text + unmapped requirement quotes
              + dangling artifacts  (auto-orchestrator.ts ~1067-1081)
    adopt:    droppedCoverage over the deterministic groundedCoverage set
  Nothing forces a retry to address what the judge flagged, and the judge
  regenerates its list from scratch each round — the original mx5 run produced
  three DISJOINT missing-lists across three rounds. So `missing` can never be
  driven to zero, the loop always burns its full budget, and the run always ends
  with the "no task fully owns" warning. v0.23.1 stopped the plan INFLATING while
  that happens; it did not fix this.

WHY IT IS BLOCKED
  Redesigning what the gate reads is premature while the requirement channel it
  would read is only 38-42% reproducible (TASK 3). Fix extraction first.

WHEN UNBLOCKED, THE QUESTION IS
  Should the loop continue on the stochastic judge channel at all, or only on the
  deterministic unmapped-requirement channel? Note the judge channel is what
  catches areas the requirement extractor MISSED, so deleting it outright trades
  one blindness for another. Measure before choosing.
